# 记录笔记：从判断到落库

把「刚刚想清楚的一件事」变成**向 Obsidian 添加的一篇笔记**，且下次能直接用到。默认产出经验，不是日志——写「某天下单报了什么错」没人回看，写「看到这个报错先查什么」才会被第二次用到。

## 0 先定位规则，不要凭本 skill 硬套

1. **解析 vault（按顺序，命中即停）**：
   1. 用户明确给的路径；
   2. 从当前目录向上找 `.obsidian/`，其父目录即 vault；
   3. `~/.config/note-record/config.json` 的 `vaultPath`；
   4. 若 `~/Notes/AGENTS.md` 存在，用 `~/Notes`（本库默认值，不是硬编码）；
   5. 都没有 → 问一次绝对路径，`mkdir -p ~/.config/note-record` 后把 `{"vaultPath": "<绝对路径>"}` 写入 `~/.config/note-record/config.json`。
   解析后先确认 `<vault>/AGENTS.md` 存在；不存在就说明这不是本 skill 适用的库，改用通用流程或停下问用户。
2. 按顺序读：`<vault>/AGENTS.md` → 命中的子目录 `AGENTS.md` → `<vault>/.agents/docs/COMMANDS.md`；再找 `note-schema.md`（本库在 `.agents/docs/design-docs/` 下）与 `.agents/docs/STYLE.md`，存在时读。
3. **仓库规则优先于本 skill。** 冲突时按仓库执行，并在交付报告里点明冲突点。
4. **数字与落点以工具输出为准。** 篇幅、小节数、定位字数等阈值在库里的 `lib/single.py`；目录名、模板与默认落点在 `make` 脚本、`vault.py` 与各级 `AGENTS.md`。本技能给判断与流程，不替目标库发明路径。

### 两种落库方式

| 场景 | 做法 |
| --- | --- |
| **vault 有 `make` 工具链**（本库 `~/Notes`） | 用 `<vault>` 的 `make`：`make -C <vault> find` → `make -C <vault> new` → `make -C <vault> note` → `make -C <vault> check` → `make -C <vault> wb-render` → `git -C <vault> commit`。第 1–8 步即标准流程。 |
| **没有 `make` / 不在 vault 内** | **优先用 Obsidian CLI**（`obsidian`）；CLI 不可用时，再用目标 host 的 Obsidian 写入工具。复用第 1、3、4、5 步的判断；把第 2、6、7 步的机器校验换成 CLI 验证或写入工具的 `dryRun` + 人工确认。 |

> **原则**：判断逻辑（第 1、3、4、5 步）与 vault 无关，永远复用；工具链（第 2、6、7、8 步）按环境切换。

**采集器只做上游**：`second-brain` 这类自动采集工具只写 `00_收件箱（Inbox）/` 或独立 staging vault；正式笔记仍走本 skill 的判类型、查重与 `make check`。不要让 auto 模式直接写 `02_领域` / `03_资源` / `01_项目`。

### 写还是不写

不是每个结论都值得落库。先过五问：

1. **能复用到别处吗？** 能 → 优先 `area`；只在当前项目/事故里有意义 → `project`；只在这次对话里有意义（临时命令、一次性上下文）→ 不写。
2. **下次会翻回来看吗？** 不会 → 不写。
3. **有证据吗？** 没有 → 补证据，或明确标成推断；不要写成定论。
4. **和已有笔记重复吗？** `make find` ≥0.60 → 合并/链接，不新建。
5. **用户明确要求记吗？** 没有，只是聊天中顺带提到 → 先确认；用户说「可能/也许/先看看」→ 不写。

例外：用户明确说「先记草稿」→ 落 `inbox`，标 `status: inbox`，后续再分流；用户说「别记」→ 不写，已写则说明路径并询问是否删除（不要擅自删）。

### 确认强度

| 场景 | 动作 |
| --- | --- |
| 用户明确说「写笔记 / 记一下 / 存到笔记里」 | 直接执行，不再二次确认；结束时给路径与校验结果 |
| 追加到已有笔记（用户已明确说记） | 直接追加，报告追加的小节与位置；不新建文件 |
| 用户只是讨论出一个结论，没说记 | 先给「类型 + 落点 + 一句话」，问一句「要我记成这篇吗？」 |
| 用户说「可能 / 也许 / 先看看」 | 不写；除非用户随后明确要求 |
| 用户说「先记草稿」 | 落 `inbox`，不强行分类 |
| 用户说「别记 / 不用记」 | 不写；已写则说明并询问是否删除 |

## 1 判类型

### 分类条例（有条例、有规范）

**核心原则**：每篇笔记只承载**一个核心判断**。一句话里出现两个判断 → 必须拆两篇。

**判定流程**（按顺序匹配，首中即停）：

| 顺序 | 判定题（全是/全否） | 是 → 类型 | 说明 |
| --- | --- | --- | --- |
| 1 | 材料完全未消化、只是暂存 | `inbox` | 收件箱；后续再分流 |
| 2 | 是当天的随手记、状态记录、带 `daily` 标签 | `journal` | 当日随手记，用 `TP_Journal` |
| 3 | 是一本书/一篇长文的**消化笔记**（非原文转存） | `book` | 一篇一本，落 `028_读书` |
| 4 | 是工具用法、速查表、参考资料、API 对照 | `resource` | 用 `TP_Resource` |
| 5 | 是**一个专题的全景索引/导航页**（不含实质判断） | `moc` | 用 `TP_AreaMOC` |
| 6 | 结论**能脱离当前项目/事故独立成立**、可复用到别处 | `area` | 用 `TP_Area` |
| 7 | 结论**只在当前项目/这次事故里有意义**、有时效性 | `project` | 用 `TP_Project` |

**判断「能否独立成立」的三个证据**（满足任一即可判 `area`）：
- 能把结论抽象成「看到 X 现象先查 Y」的**判断规则**
- 能列出**适用边界**（什么场景不适用、已知缺口）
- 结论引用的是**通用原理/规范/源码**，而非项目私有代码

**冲突处理**：同时符合 `area` 与 `project` 时 → 写 `area` 笔记，`project` 页只留一行 `[[链接]]`。

### 会议与决策怎么落

不要为了「会议」「决策」新造 frontmatter 类型——本库 `verify.py` 按路径分类，`note-schema.md` 也没有这两个类型；只在 skill 里加 `type: meeting` 会直接落成不合规笔记。

按结论的归属复用现有类型：

| 材料 | 落点 | 正文骨架 |
| --- | --- | --- |
| 项目内的决策/评审/事故复盘，只在当前项目有意义 | `project` | 背景 → 选项 → 结论 → 后果 → 复核条件 |
| 决策能抽象成通用判断，换项目也成立 | `area` | 同 area 模板；结论用 `[必会]`，边界用 `[坑]` |
| 当天站会/1:1/随手会议纪要，没有独立结论 | `journal` | 参会人 → 议题 → 讨论 → 行动项；必要时链到 project |
| 还没想清楚是纪要还是决策 | `inbox` | 先原样收，再分流 |

会议里出现的每个**重要决策**，单独成一篇 `project`/`area` 笔记，并在会议笔记里 `[[链接]]`；不要把多个决策塞进一篇会议纪要。原始 transcript 不进正文，放 `04_归档（Archive）/` 并在文末给路径。完整骨架与反模式见 `references/decision-meeting.md`。

### 类型 → 创建方式与落点

**优先用 `make new` 建骨架**：它按模板渲染、按类型自动编号（`area`）、做写前查重；落点由 `INTO` 或类型默认目录决定。下表的路径是**本库当前**的实际目录，换库时以目标库的 `vault.py`、`Makefile` 与目录 `AGENTS.md` 为准。`make new` 会为不存在的 `INTO` 建目录——路径写错就会长出一棵新树，所以 `INTO` 必须指向已存在且命名合规的落点（`0XX_` / `0XXNN_` / `NN_`，或本库的 `0NN_主题` / `0X_项目`）。

| 类型 | 创建命令 | 模板 | 落点（本库当前） | 必填属性（见 `note-schema.md`） |
| --- | --- | --- | --- | --- |
| `area` | `make new KIND=area TITLE="标题" INTO="<分区目录>"` | `TP_Area.md` | `02_领域（Areas）/0XX_领域/0XXNN_专题/NN_分区/`（按目标目录 `AGENTS.md` 决定到哪一级） | `tags`（≥2；本库约定专题/分区/主题三项）`updated` `by` |
| `resource` | `make new KIND=resource TITLE="标题" INTO="<主题目录>"` | `TP_Resource.md` | `03_资源（Resources）/0NN_主题/` | `tags`（必填；建议 2–3 项）`updated` `by` |
| `project` | `make new KIND=project TITLE="标题" INTO="<项目目录>"` | `TP_Project.md` | `01_项目（Projects）/0X_项目/` | `type` `status` `deadline` `created` `updated` `by` |
| `book` | `make new KIND=book TITLE="《书名》"` | `TP_Book.md` | `02_领域（Areas）/028_读书/` | `author` `status` `updated` `by` |
| `inbox` | `make new KIND=inbox TITLE="标题"` | `TP_Inbox.md` | `00_收件箱（Inbox）/YYYY-MM/` | `title` `source` `published` `status` `updated` `by` |
| `moc` | 手工；新专题由 `make area` 生成 | `TP_AreaMOC.md` | `<专题>/00_<名称>-知识地图.md` | `tags`（≥1）`updated` `by` |
| `journal` | 手工 | `TP_Journal.md` | `05_日志（Journal）/YYYY/YYYY-MM-DD.md` | `created`（或 `date`）`tags`（含 `daily`） |

插件采集的 inbox 用 `source_url` / `published_at` / `saved_at`，与规范字段等价，不要为改名把采集结果重写一遍；新写笔记用规范名。

### 输出要求

判类型时必须在任务文件/交付报告里写明：**类型 + 落点目录 + 命中的判定题编号 + 为什么不是相邻类型**。

## 2 查重（不能跳）

```bash
make find Q="<核心关键词，用术语不要用标题原话>"
```

| 最高分 | 动作 |
| --- | --- |
| ≥ 0.60 | **不新建**，合并进那一篇，在原位置加小节 |
| 0.35–0.60 | 可以新建，但正文必须链接那一篇并说明差异 |
| < 0.35 | 直接新建 |

`make new` 建文件时会跑同一档查重：命中 ≥ 0.60 直接拒绝新建，确要新建用 `FORCE=1`。无论用哪种方式，结果都要记进任务文件。

无 `make` 的库：`grep -ril "<术语>" --include="*.md"` 列候选，人工判读，grep 命令与结果一并贴进任务文件。

**记痕**：从 `.agents/harness/tasks/_TEMPLATE.md` 复制一份 `T-YYYYMMDD-<slug>.md`，保持 `status: open`，把原始输出、「选了哪一档、为什么」贴进去；同时在本库 `.agents/harness/INDEX.md` 的「活跃任务」表加一行。收尾改 `status: done` 并同步 INDEX。**没有这条记录等于没查。**

## 3 写成经验，标出处

改写对照见 `references/experience-vs-log.md`。速查：

| 日志的味道 | 经验的样子 |
| --- | --- |
| 「7 月 3 日下单报 EOF」 | 「裸 EOF 说明请求已写出、对端零响应」 |
| 「我先查 A 又查 B，最后发现 C」 | 「先查 A 再看 B；C 才是根因，顺序有理由」 |
| 「我这次踩坑是……」 | 「最容易撞上的场景是……」 |
| 「修好了」 | 「改哪个参数、为什么管用、怎么验证」 |
| 大段背景交代 | 结论先行，背景压成一句 |

每篇必须有的五件东西：

1. **一句话定位**：≤40 字，只含一个判断。写在标题下一行。
2. **可证伪**：怎么验证、什么现象说明修错了或结论错了。
3. **边界**：不适用的情况、已知缺口。别把没证据的部分写成定论。
4. **provenance**：区分「实测」「源码/文档」「推断」；推断显式标出来。
5. **出处**：来源必须有权威性，且能点回去。

### 出处的两条规矩

- **一手优先**：官方文档、源码、规范原文、原始归档。博客/转述/二手结论必须标「二手」；不写「网上说」「据说」。
- **落在文末**：`## 引证`（本库惯例）或 `## 出处`，一行一条：
  `- 《YYYY-MM-DD 标题》（归档，Nk 字）` 或 `- 标题 · URL · 版本/访问日期`。
  正文里某个关键结论也可以单独给 `出处：…` 行。

机器会验两件事（`lib/single.py` 的 `area_style_errors` / `_source_authority_errors`）：

1. 有没有来源——既无「引证/出处」小节、也无链接与归档 → ERROR。
2. 来源是不是一手——域名命中 `OFFICIAL_HOSTS`（发布方自己的站点，如 `go.dev`、`kubernetes.io`、`github.com` 源码）、或标了「（归档）」/ 指向 `04_归档` 算一手；其它域名必须在正文标「二手」并说明原始出处，否则 ERROR。

翻译站、聚合站、个人博客都属于二手：保留它们可以，但同一行要给出原文。案例：`原文（英文）：<官方地址>` 下一行 `译文（二手）：<译文地址>`。

## 4 选模板 + 填属性

模板在 `90_模板（Templates）/TP_*.md`。优先用 `make new`（第 1 步的表）；手工从模板复制只用于没有 `make` 的库，或 `make new` 不支持的类型（`moc` / `journal`）。

模板给骨架，不是填空：小节标题可以改，但模板要求的结构不能省。分区笔记（`area`）的面包屑、页脚回链、末节「与其他章节的衔接」是硬约束；`book` 用 `TP_Book` 的 `核心主题 / 关键点 / 分析`；`journal` / `inbox` 是记录形态，不套分区体例。frontmatter 按 `note-schema.md` 填，**不新造字段**——要加字段先在 schema 里登记。

会议纪要、决策（ADR）的正文骨架见 `references/decision-meeting.md`；类型仍用第 1 步表里的 `project` / `area` / `journal` / `inbox`，不要新造 frontmatter 类型。

三条容易写错的属性：

- **`tags`**：只对 `area` / `resource` / `moc` 是必填。`area` 本库约定三项（专题、分区、主题），别只写一项；`book` / `journal` / `project` / `inbox` 用各自字段，**不要把书名、作者、年份、阶段塞进 tags**。
- **`updated`**：**新笔记**写今天；**改写旧文**取该文件最后一次 git 提交日期（取不到用 mtime），不写当天——否则「最近一次改写」失去意义。
- **`by`**：新写一律 `agent`；改写旧文保留原值，别把 `human` 的旧文改成 `agent`（那是伪造历史）。

**book 的额外动作**：写完在 `02_领域（Areas）/028_读书/_读书汇总.md` 加一行（书名双链 / 作者 / 状态），否则 `make check-books` 会报「缺行」。汇总表只允许这三列。

**新专题**：`make area NAME=0XXNN_名称` 只建骨架（入口页 + 该目录 `AGENTS.md` + `README.md`），**不会**改父级目录树。之后：

1. 填入口页的分区名、`AGENTS.md` 的「目录职责」、`README.md` 的「里面有什么」——空白骨架能过检查，但说不出这个专题收什么，就等于没建。
2. 在**父级** `AGENTS.md` 的目录地图/骨架里补一行：一级领域补到根 `AGENTS.md`，专题补到所属 `0XX_领域/AGENTS.md`。
3. 跑 `make check-harness`，确认目录入口与地图不漂移。

## 5 写正文

按 `.agents/docs/STYLE.md`：第一人称单数、单句 40 字内、结论先行、术语首次给原文。

分区笔记（`area`，scope=`single`，`make note` 与 `make check-single` 机器验）的硬约束：

- 每个知识点小节标题带 `[必会]` / `[坑]` / `[版本]` 之一，**至少一个 `[必会]`**；「与其他章节的衔接」「引证/出处」是结构节，不带标记；
- 最后一节是 `## 与其他章节的衔接`；
- 标题下一行 `> 一句话定位：…`，40 字内（机器放到 50，别贴着机器写）；
- 面包屑 `> 上级：[[00_xxx-知识地图]]` 与页脚回链（`上级：` 出现两次）；
- 有出处（见第 3 步）；
- 标题不带 `NN_` 编号，编号在文件名上；
- 篇幅与小节数：阈值在 `lib/single.py`，超了按 `make note` 的 WARN 判断是不是装了两件事；
- 链接一律 `[[短链]]`，不写死路径。

`book` 不走这套分区体例：用 `TP_Book`，前三节是 `核心主题 / 关键点 / 分析`，关键点不少于 3 条；写完补 `_读书汇总.md`。

会议/决策：重要决策单独成篇，会议笔记只做索引；正文骨架见 `references/decision-meeting.md`。项目内决策按 `project` 落，能独立复用的按 `area` 落。

## 6 单一性检查（写完立刻跑）

```bash
make note P="<笔记路径>"
```

| 判定 | 含义 | 动作 |
| --- | --- | --- |
| 单一知识点 | 过 | 继续第 7 步 |
| 待确认 | 篇幅或小节数偏大 | 回答自检三问，确认不是罗列 |
| 需处理 | 有 ERROR（含体例、出处硬伤） | 按提示拆，或补标记/出处/定位 |
| 聚合页 | 知识地图 / 汇总 / 附录 / 学习自测 | 不做单一性判定；只做索引，不复述正文 |

无 `make` 的库：数一级标题（只允许 1 个）、读标题下定位、人工答自检三问，把结论写进任务文件。

「一个文件一个知识点」是硬规则，聚合页（知识地图 / 汇总 / 附录 / 学习自测）除外——它们的职责就是装多件事。真正的判断靠那一行定位：**写不出这一篇的一句话，就是没想清楚，别急着往下写。**

受检范围是**活笔记**：收件箱、归档、日记、模板、附件、隐藏目录（`.archive_*` 这类拆分前的初版长文）都不参与。隐藏目录不是内容目录。

## 7 校验

```bash
make check                 # 全库
make check-<域>            # 单域：areas / books / folders / harness / inbox / links / schema / single / stale / style
```

必须 0 ERROR 才算完。红点判读见 `references/vault-checks.md`。**不要把预存的红点说成本次引入的**：改动前后各记一次「合计」，数字没变就是没引入；变了再看新增条目的路径是不是自己的文件。

存量处理有两条规矩：

- 新增断言打在存量笔记上，用 `make baseline` 把存量降级成 `INFO`（存量），别把历史问题算进这次。
- **基线不保护你动过的文件**：`git diff HEAD` 里出现过的笔记，就算账上有旧欠也照报 ERROR。改一篇旧笔记＝顺手把它补到合规，补不动就说明为什么，别指望基线兜住。

无 `make` 的库：按 `references/vault-checks.md` 的清单逐条人工过（定位、标记、末节、出处、面包屑、双链、frontmatter），把结论写进任务文件。

**新建或改写分区笔记后，要手改专题 MOC 的目录表。** 模板里叫「分区索引」，现有 MOC 可能写成「二、目录」并按分区列笔记；脚本查不出索引漏项，这是唯一一处「校验全绿但读者找不到」的缝。

## 8 记痕、刷新统计、提交

- 任务文件更新检查点；踩了坑写 `.agents/harness/trace/YYYY-MM-DD-主题.md`；一条能改变下次做法的结论，蒸馏进 `.agents/harness/memory/lessons.md`。收尾时把任务文件的 `status` 改成 `done`，并同步 `.agents/harness/INDEX.md` 的「活跃任务」表。
- **每次新增或改写笔记之后都跑 `make wb-render`**，刷新首页与工作台统计页。`scope=stale` 会把「面板数字与磁盘不一致」报成 ERROR，所以顺序固定：**写完 → 渲染 → 再提交**；渲染改的两个文件单独一个 chore 提交，别和内容混。
- 一次只改一类：新增笔记 / 改写 / 渲染出的统计页，分开提交。`book` 的 `_读书汇总.md` 与正文属于同一次内容改动，一起提交。
- **不 `git add -A`**：`.obsidian/plugins/*/data.json` 这类插件写回不入库。
- 提交信息写「为什么这么记」，不写「更新笔记」。

## 交付报告（四段，缺一段都算没交付）

1. 路径 + 创建命令 + 为什么落这里（含查重档位与理由）；
2. 这篇的一句话定位 + 核心结构；
3. 校验命令与真实输出（含 `make note` 判定）；
4. 出处清单 + 明确没做的事（已知缺口、待确认项）。

不要只说「已记录」。

## 常见失败

| 症状 | 原因 |
| --- | --- |
| `make new` 报「需要 --into」 | `area` / `resource` / `project` 必须传 `INTO=...` |
| `make new` 报「已有高度相似的笔记」 | 查重命中 ≥ 0.60；先合并，确要新建加 `FORCE=1` |
| 路径写成 `02_领域/…` | 本库目录带双语后缀；用 `make new`，或写全名 `02_领域（Areas）/…` |
| `book` 笔记写进了 `04_归档` | `book` 的消化笔记落 `028_读书`；`04_归档` 只读保真 |
| `check-books` 报「缺行」 | 没在 `028_读书/_读书汇总.md` 加行 |
| `tags` 写成「书名/作者/年份」 | 那是 `book` 的 frontmatter 字段，不是 tags |
| `make note` 报「缺 [必会]/[坑]/[版本] 标记」 | 没从模板建，手写了小节标题 |
| 报「末节是「X」，应为「与其他章节的衔接」」 | 把「引证」「相关」放在了最后 |
| 报「没有出处」 | 补 `## 引证` 或给链接/归档来源，见第 3 步 |
| verify 报「缺 tags」 | 没从模板建，手写了 frontmatter |
| 双链点了没反应 | 文件名含半角 `\|` |
| 入口页找不到新笔记 | 忘了更新专题 MOC 的目录表，脚本查不出 |
| 同一概念两篇各写一遍 | 跳过第 2 步查重 |
| 检查突然几百条 ERROR | 仓库根出现运行目录（`.venv/`、`node_modules/`），看 `references/vault-checks.md` |
| 技能里的数字与工具输出对不上 | 抄了旧阈值。改成读 `lib/single.py`，别在技能里写死 |
| vault 解析到了错误的库 | 先看 `~/.config/note-record/config.json`；显式路径 > 配置 > walk-up；写前确认 `<vault>/AGENTS.md` |
| 会议纪要被写成一篇大杂烩 | 重要决策单独成篇，会议笔记只留链接 |
| 新增 `type: meeting` 后 verify 报错 | 本库按路径分类；不要新造类型，先改 `note-schema.md` 与 `verify.py` |
| 用户说「可能/也许」，却落库了 | 先过「写还是不写」五问；不确定就先问 |
| 采集器把笔记写进了正式分区 | 采集器只写收件箱/staging，正式落库走本 skill |

## 不适用

- 收件箱剪藏整理 → `clip-normalize`
- 榜单文章拆书单 → `book-split`
- 首页/工作台数字刷新 → `workbench-maintenance`
- 会议/研究/决策的实时自动采集 → `second-brain` 等采集器只写收件箱/staging；正式落库仍走本 skill
