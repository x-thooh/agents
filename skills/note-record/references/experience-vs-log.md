# 经验 vs 日志：怎么改写

同一件事，日志让人无感，经验让人下次能照做。差别不在文采，在**有没有可迁移的判断**。

## 三条判据

1. **换个人、换个项目还成立吗？** 不成立 → 那是日志。
2. **读完知道自己下一步做什么吗？** 不知道 → 还停在描述。
3. **能被证伪吗？** 说得出「什么现象说明我错了」才算结论。

## 改写对照（真实案例，已脱敏）

### 例 1：从「某次事故」到「判断规则」

日志写法（不要）：

> 7 月 3 日插件下单报 `EOF`。我先怀疑依赖，查了 x/net 版本，又查了供应商 IP 白名单，
> 最后发现是 GOROOT 指向了旧版本。改完就好了。

经验写法：

> 构建报错落在标准库或依赖内部时，第一步不是查依赖，是对齐 `go version` 与
> `go env GOROOT`。两者不同源时，任何依赖都会以同一形态失败，而报错文本里不会提版本。

差别：时间、人物、探索顺序全部删掉；留下的是「触发条件 → 第一动作 → 为什么」。

### 例 2：从「我修好了」到「为什么这个改动管用」

日志写法：

> 加上 `ForceAttemptHTTP2: true` 之后问题消失了。

经验写法：

> 它恢复两件事：握手形状（ALPN 从空变回 `[h2 http/1.1]`）与断链语义（已写出的 POST
> 从「不可重放」变回「可安全重放」）。后者才是解决的原因——不是让对端不再断链，
> 而是让同一次断链不再等于一次不可挽回的失败。

差别：从「症状消失」进到「机制」，并且指出**哪一半是根因、哪一半是兜底**。

### 例 3：把探索顺序变成判定链

日志写法：

> 我查了 A，不对；查了 B，也不对；最后查 C 才发现。

经验写法：

> 判定链：① 打印 `resp.Proto`；② `curl -sv` 看 ALPN；③ 对齐时间线。
> 第①步最容易被跳过，因为参数看起来只是「设了 TLS 版本」。

差别：顺序保留，但每条都给出**为什么排在这里**，读者可以只跑第①步。

## 必须删掉的东西

- 日期、时间线、「今天」「昨天」；
- 人名、工单号、具体单号、内部域名（用 `<供应商网关>` 这类占位）；
- 探索过程里被排除的错误假设的**叙事**（结论可以留：它现在是「误区表」的一行）；
- 「我觉得」「应该是」「大概率」——要么给证据，要么明确标成推断。

## 必须留下的东西

- **触发条件**：什么现象出现时该翻这篇；
- **第一动作**：先跑哪条命令、先看哪个字段；
- **机制**：为什么这样能解决，而不是别的写法；
- **边界与缺口**：什么情况下它不成立，哪部分没有证据；
- **provenance**：`[实测]` / `[源码]` / `[推断]` 三种标注，混用等于骗人。

## 自检三问

1. 只读「结论」一节，能判断该不该继续往下看吗？
2. 把任意一节删掉，结论还成立吗？成立的那节是凑数的。
3. 有哪一节可以原样搬去另一篇？有，说明它不属于这里。
