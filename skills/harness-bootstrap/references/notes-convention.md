# 语料生命周期与模块作用域（笔记怎么写、模块怎么定）

> 本文件从 `../SKILL.md` 拆出（[§五.5](../SKILL.md#5-状态只三类--写入门槛)：参考材料超过 100 行或反复查表用的，外置）。
> 正文中的 `§X` 指 `../SKILL.md` 的章节；需要精确跳转时读该文件的对应标题。

`.harness/` 只存三类状态，各有各的寿命：

| 位置 | 放什么 | 寿命 |
| --- | --- | --- |
| `deliverables/` | 门记录与证据，按阶段归档 | 阶段结束即冻结 |
| `tasks/` | 活动任务 | 有限保留 |
| `memory/` | 教训与架构决策（`memory/trace/` 放失败过程，可不 git 入库） | 永久 |

写入门槛只有一条：**它能改变下一次的做法**。失败原因能，进度流水不能。

`.harness/specs/` 不是越写越长的抽屉。一篇笔记只承载一个决策，用目录承载状态：

| 位置 | 含义 | 允许的骨架 |
| --- | --- | --- |
| `.harness/specs/notes/proposed/` | 还没拍板 | Problem → Proposal → Alternatives → Acceptance criteria → Risks（允许将来时） |
| `.harness/specs/notes/implemented/` | 已拍板 | Problem → Decision → Alternatives → Consequences（**禁** Proposal / Plan / Migration plan / Acceptance criteria——计划腔不算现实） |
| `.harness/specs/notes/rejected/` | 被否掉 | 冻结的提案，判定写在 `Status: rejected — <理由>` |

文件名 `yyyy-mm-dd-<slug>.md`，头五行固定，多一行都不行：

```yaml
title: 用模块 id 而不是目录路径标作用域
date: 2026-10-23
status: proposed
scope: api.users.create
summary: 目录装不下功能边界，改用能 grep 到的锚点定位模块
```

`summary` ≤ 120 字，是**索引行与指针行的唯一来源**（下游不重新摘要，否则同一件事有两个措辞）。正文超 100 行就把细节外置成同目录 `<slug>.details.md`，主文件只留结论与链接（[§五.5](../SKILL.md#5-状态只三类--写入门槛) 的阈值）。

硬约束（不写条数——写死数字就跟内容漂移）：

- **写入门槛：代码能推出的，一律不写**。能靠读代码/跑测试反推的决策不写笔记——写了没人读，还稀释真决策。所以每篇必须有一个 `## 不显然之处` 段：它就是「当初不写清楚会让人做错」的那一点。段在但空着 → ERROR（形状可检，内容人判）。

- **一篇一个决策**：改结论不改旧篇，新写一篇并互相链接（`supersedes`），作废不删。
- **状态是位置**：`Status:` 行只是投影，必须与所在目录互校；换状态用 `git mv`——位置有版本记录，字段没有（字段会被忘改，被改也不留痕）。
- **作用域是字段，按模块划分**：`scope:` 取值是模块标识（`api.users.create`、`cli.import`、`svc.payment`；`*` 表示全仓），不是目录路径。生命周期用位置、作用域用字段——两条轴两套编码，不兼职。**缺 `scope:` 不等于全仓**，是没声明归属，报 ERROR（UHP 原则 4：缺失不是空）。注意：规则覆盖按目录（[§五.6](../SKILL.md#6-覆盖默认少而广)），决策作用域按模块——两条不同的轴，不互相借用。

- **`AGENTS.md` 不放决策正文**：要露出来就放脚本生成的指针行（一行一链接 + scope），手改即漂移，重新生成后比对不一致即 ERROR。查询按模块 id 最长前缀向上找，找不到就是没定。这也是 [§五.1](../SKILL.md#1-五层分层加载顺序即分层顺序) 单向引用的落地：入口层只指向知识，不承载知识。
- **归属只问一个问题**：`.harness/specs/` = 现在是什么 · `.harness/specs/notes/` = 为什么这么定 · `.harness/tasks/` = 还没做什么 · `.harness/memory/trace/` = 这次为什么出事。放错地方的症状是：同一个决策被反复重议。

**模块 = 有独立入口或独立契约的最小单元，不是目录。** 合格形态三种：对外接口（一个 HTTP route / 一个 gRPC method）、可执行入口（一个 CLI 子命令 / cron 任务 / 迁移脚本）、完整最小功能点（跨多个目录但只有一个验收场景）。判据三问：能单独被调用吗？有独立契约（输入、输出、失败码）吗？坏掉时能单独定位和回滚吗？——三问有两问答否，它就属于别的模块。

因此**目录对不上模块**（一个目录可装十个模块，一个模块可跨五个目录），不能拿目录树当模块树。模块靠**锚点**定位：

| 模块形态 | 锚点（必须能在代码里找到） |
| --- | --- |
| HTTP / gRPC 接口 | 路由字面量 或 service/method 名 |
| CLI / cron / 迁移脚本 | 入口文件路径 + 子命令名 |
| 最小功能点 | 验收场景名（测试 id） |

锚点找不到 = 幻影模块，ERROR（清单里写着、代码里没有，比没写更坏）。

**清单一律 AI 起草、人拍板，AI 不得自己认定。** 起草时每条必须带证据（`文件:行`、路由字面量、`service.method`、测试 id），拿不出证据的条目不许进草案——这是 [§十一](../SKILL.md#十一记忆树树--授权--记录)「只能 remember 不能 observe」在模块轴上的同一条规矩。人批准后把 `modules-confirmed: <commit>` 记进 `decisions.md`；AI 重扫出的 diff 只有人批过才进清单，否则就是自动漂移（那就是第二个事实源）。

**批准之后三方对账，冲突以事实为准**——裁决顺序是 **代码事实 > 人写清单 > 目录布局**：

| 对账 | 不一致时 | 强度 |
| --- | --- | --- |
| 清单 ↔ 锚点（功能事实） | 锚点没了 → 改清单不改代码，ERROR；新锚点无人认领 → WARN 提醒起草 | 强 |
| 清单 ↔ 目录（布局） | 目录有、清单无 → WARN（可能只是容器目录）；清单有、目录无 → 不判（模块本就跨目录） | 弱 |
| 目录 ↔ 锚点 | 不构成对账——目录没有判定权 | — |

别把这条和下面「索引只派生」混为一谈：`.harness/INDEX.md` 是纯机械派生，重新生成后逐字节比对；模块清单里含人的判断（这个功能算不算独立模块），只能「草案派生 + 批准入册」。两者都防漂移，但一个不许人碰，一个必须人碰。

`scope` 校验分三档，因为模块会重构而笔记是历史事实：`proposed/` 必须命中当前清单（否则 ERROR，提案连改哪个模块都说不清）；`implemented/` 与 `rejected/` 失效降级 WARN（历史不因重构返工）；归档区不校验（冻结内容不追新）。
**禁止人手写的索引。** 目录即唯一归属：人手维护的 `INDEX.md` 必然漂移，而漂移机检不出来（索引和内容都是自然语言）。要总览就由脚本生成派生视图，断言 = 重新生成后与磁盘逐字节一致，不一致即 ERROR。派生的数也一样（scope 清单、无断言规则数这类）——本 skill 踩过：手写 `unanchored_rules: 3`，和「不写死计数」直接冲突。

**日期是首次提出日**，以 git log 为准，不是落地日——落地日会被「后来补的文档」冒充。
