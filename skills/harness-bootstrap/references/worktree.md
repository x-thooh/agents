# 任务级 worktree：一个任务一棵树

> 规格本体在 `../SKILL.md` [§十四](../SKILL.md#十四任务级隔离一个任务一棵树)「任务级隔离」；本文件解释取舍、落地细节与
> 踩坑。`§X` 指 `../SKILL.md`。命令的参考实现在两套模板的 `.harness/scripts/wt.py`。

## 为什么不是「在主工作树上切分支」

切分支要先处理未提交的改动，做法只有两个：`git stash` 或先提交一个半成品。前者让脚本
替人保管工作——保管丢了没人发现，而且「刚才 stash 的那份在哪」是个只有操作者知道的
问题；后者把没做完的东西变成历史，`CM006`（一个提交一件事）当场失效。

worktree 是旁路：主树保持原样，任务在另一个目录里长，两条线互不打扰。这也是
`scripts/round.py` 用 `--detach` 临时检出 `HEAD~1` 的同一个理由——**脚本不该替人保管
未提交的改动**。

## 三条约定

| 约定 | 值 | 为什么 |
| --- | --- | --- |
| 目录 | 同级 `<repo>-wt/<task-id>` | 放在仓库里就进 `git status`，`git add -A` 一次就收进提交 |
| 分支 | `task/<task-id>` | 与看板 id 一一对应，断言才认得出哪棵树属于哪个任务 |
| id | `tasks/board.json` 的 `id` | 树是任务的下游：先有任务，才有树 |

约定之外没有默认识别：手工建的树（别的分支名、别的目录）`wt.py` 认不出，`worktree`
scope 也不认。这不是缺陷，是「约定大于配置」的另一面——放宽识别等于让收尾时多一种
「我以为它会自己找到」的期待。

## 收尾四步，顺序不许颠倒

1. 跑门禁（`make check`），绿了再提交；
2. 提交（`git add -A && git commit`）；
3. `git worktree remove`——**整条流程唯一不可逆的一步**，它会连未提交的改动一起丢掉；
4. `git branch -d` 删分支，`git worktree prune` 清残档。

`wt.py finish` 把 3、4 两步包起来，并在动手前查两件事：工作区干净（否则拒绝，列出脏
文件）、分支已合并进 base（否则拒绝，提示先合并或走 PR；确认要连未合并的分支一起删，
才加 `--force`）。这两个前置条件是「先提交再删树」这句口号的可执行版本。

## 判据与判不了的那条

`scope=worktree` 判两件事，都要求 harness 根目录**就是**仓库根：

- `WT001`（ERROR）树在，任务已 `done` 或不在看板——收尾只做了一半，本机留下的残树。
- `WT002`（WARN）树已开，任务还是 `todo`——顺序反了：先开树再改状态，或状态忘了改。

**「忘了开树」判不了**：任务可能在别人机器上做，本机没有树是正常的，判成 ERROR 等于让
每个人的机器互相告状。这条写在 `AGENTS.md` 的硬规则里靠人守，不用弱断言假装守住。

根目录不是仓库根时记「判不了」而不是通过：模板本身是某个大仓库的子目录，那时
`git worktree list` 返回的是**别人**的树，拿它判就是张冠李戴。

## 四类踩坑

1. **`already checked out`**：同一分支不能被两个 worktree 同时检出。先 `git worktree list`
   看是谁占着——通常就是上一次没收尾的树。
2. **删树被拒**：树里有未提交或未跟踪文件时 `git worktree remove` 会拒绝。这是保护，不是
   故障；`--force` 能绕过，但它绕过的是你自己没提交的工作。
3. **手工删了目录**：`rm -rf` 掉树目录后元数据还在 `.git/worktrees/`，`git worktree list`
   仍列着它。跑 `git worktree prune`，不要手改 `.git/`。
4. **软链指向主树**：把技能目录软链进宿主 agent 的目录时，软链指向的是**主工作树**。
   树里改的文件宿主读不到——worktree 适合「改 + 跑门禁」，不适合「改完让宿主立刻加载」。
