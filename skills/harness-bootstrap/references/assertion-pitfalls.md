# 断言设计通用坑

> 编号是稳定标识（代码与文档里多处按号引用，如「坑 #11」），所以**只接在末尾追加，不重排也不删号**。
> 这里不写条数：「N 条」是写死的事实，添一条就两处一起说谎，而没有任何断言会报。
>
> 本文件从 `../SKILL.md` 拆出（[§五.5](../SKILL.md#5-状态只三类--写入门槛)：参考材料超过 100 行或反复查表用的，外置）。
> 正文中的 `§X` 指 `../SKILL.md` 的章节；需要精确跳转时读该文件的对应标题。

1. 基线只按（域, 路径）记，同一文件的新问题照样通过——必须带消息指纹。
2. 「工作区干净」的判断不排除易变路径（时戳、缓存类文件），前置检查会永远拒绝执行。
3. 模板/占位符内容造成假断链，链接检查要跳过模板目录。
4. 索引/聚合类文件会混进内容文件判定，按路径分类处先排除特殊命名。
5. 文档写了、代码没实现 = 没有，判据进文档那一刻代码就要跟上。
6. 「字段缺失」≠「字段为空」，规范里「空表示 X」的字段用白名单只查 key 存在。
7. 收编外部工具的字段名做别名表，别改它，否则每次它还会写回旧值。
8. 自动修文本跳过围栏代码块——代码里的「问题格式」是内容。
9. 报告必须带降级上下文，不给裸「0 通过」。
10. 匹配规则用 `match` 而非 `fullmatch`（本地化后缀会让 fullmatch 恒假，scope 静默失效），写完必做反向测试。
11. **扫到 0 个样本要报错**。路径写错、glob 失效、目录改名，三种病状一模一样：0 个文件、0 个 ERROR，和「全绿」长得完全相同。每个 scope 先断言样本数 > 0，再断言违例数。
12. **裸编号跨文件不可检**。`[§六.2](../SKILL.md#2-进度是事实流不是渲染)` 在同一个文件里可读，跨文件重排后静默指向别处，而存在性检查只能答「有没有这一节」，答不了「是不是原来那一节」。跨文件引用一律相对链接；文件内部编号可留，但重排必须人审 diff（这也是本文件自己仍用 `§X` 的边界）。
13. **反向测试不报错时，先怀疑断言本身，别以为样本没造对**。实测：判「注册面是否包含构造函数」写成 `strings.Contains(providerSrc, ctor)`，被注释掉的注册行照样算已注册，于是反向测试一片绿。修法是比对前先剥 `//` 与 `/* */` 再判。反向测试验证的是断言，不是样本——样本通常是对的，错的是那个恒真的判据。
14. **新 scope 加完不生效，先查文件名**。Go 把 `*_test.go` 排除在普通构建外：scope 文件命名成 `scope_test.go` 时 `init()` 根本不执行，注册表里没有它，`--scope X` 报「未注册」而全量跑仍「通过」——两个绿灯都不真的。任何语言都有这类「构建系统默认排除」的后缀；注册后第一件事是确认它真进了注册表，而不是看见全绿就往下走。
15. **解析工具输出要锚定分隔符，别用 `\s+`**。`go test` 末行单独打印一个裸 `FAIL`，`^FAIL\s+(\S+)\s` 会把它下一行的首个 token 当成包名，结果 9 个真实失败包全被判成「已转绿」（账本条目越多，假象越整齐）。改成锚定制表符的三段格式。同理适用于任何「分隔符有语义」的输出。
16. **别按命名约定推断符号名**。判「构造函数是否与类型对应」若用 `New`+类型名拼接，实测三处不一致（`NewGoodService→GoodsService`、`NewMerchantAppNotifySubscribeServiceV4→MerchantSubscribeServiceV4`、`NewVoucherServiceV4→OrderVoucher`），全部是假阳性。应从签名解析——哪个 `func New*` 的返回类型是这个 struct——而不是从名字猜。约定能管形状，不能当事实。
17. **账本共用同一个结构，字段语义会漂**。`AcceptedEntry.count` 在 vet 账本里是「同一 (路径, code) 的条数」，在 test 账本里根本不该有（包失败是布尔的，没有条数概念）——一个字段两个含义，正是「一个字段只有一个意思」的违反。要么拆两个结构，要么把语义写进字段名，并在不适用的账本里显式不填。共用结构省下的那点重复，会在读账本的人那里变成一次误判。
18. **剥了注释不等于剥了字面量**。坑 #13 说「比对前先剥 `//` 与 `/* */`」，剥完还有第二个藏身处：字符串。判「禁调用」时写 `"panic(" in code`，`code` 只要保留了字面量原文，`var _ = "库代码不许 panic("` 就会报 RUNT001——而正对照照样绿，因为合规样本里没有人写这种文案。修法是分层：留着原文的给「读文案」的断言（错误串标点、`%w`），另出一份把字面量内容抹成空格的给「禁调用」的断言（抹成空格而不是删掉，否则 `pa"x"nic(` 会拼回 `panic(`）。反向测试也要两种：一个正对照证明合规不发火，一条 clean 样本证明「长得像违规」不发火。
19. **判「文档里的名字是否真存在」，先判这句在说谁的仓库**。想给「文档点名的路径必须存在」上断言，直接按本仓库基址去比对——实测 94 个命中里 26 个**语义完全正确**：文档在用反引号讲目标仓库的布局（`.harness/INDEX.md`、`proposed/`、`skills/`）。多基址猜测救不回来，因为归属是「这一句在说谁的仓库」，是语义不是语法。可行的做法只有两个：（a）只判能判死的形态——相对链接（LINK004）、台账里的 code / scope 名（DOC002），其余写明人判；（b）反方向判「有了却没人说」（DLV001：交付物至少被文档提一次）。别写一个「看起来能抓漂移」的路径检查，它的误报率会把真发现淹掉。
20. **正对照的期望值不许由别处状态算出来**。给「单查 baseline 不吐 BASE014」补反方向时写成「全量跑必须报 BASE014（账本 1 条、现状 0 条）」，实测立刻红——不是守卫坏了，是测试环境不中性：`copy_root` 出来的模板里本来就有一条 `GUIDE001`，它把 `debt` 从 1 抵消成 0。这类期望最阴的地方是它**有时绿**：模板少一条无关 ERROR 就过，多一条就红，红的时候看起来像被测对象坏了，于是人会去改被测对象。修法：正对照只钉被测对象自己的契约（全量跑不许记 `not_applicable`）；凡是「账本减现状」算出来的数都不许进期望——那不是断言，是把别处的状态复制了一份，然后声称它一直在那儿。
21. **加断言前先搜有没有同契约用例，否则你加的是重复**。给「单查 baseline」加守卫测试时没先搜，写了一个 45 行的新用例，绿得很像成功；一小时后才发现 `templates/*/tests/reverse.py` 里的 `baseline_solo_case` 早在钉同一件事。判据只有一句：**摘掉守卫，看谁先红**。已有用例先红 = 你写的是重复；只有新用例红 = 它真补了空。同一条契约写第三遍的代价不是行数，是改契约时要同步三处，而那三处没有任何断言要求它们一致——重复的断言不会互相校验，只会一起漂。
