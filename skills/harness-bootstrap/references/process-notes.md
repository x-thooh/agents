# 交付刹车与 verify 脚本规范

> 判据在 `../SKILL.md` §六；这里是展开与反例。`§X` 指 `../SKILL.md`。

## 交付条件与预算（刹车）

门禁绿不等于该交付，自检绿也不等于可以无限自检：

- **最小可用，再增量**：`verify` 一次只加一个 scope，加完立刻跑。别先把整套写完再回头调错——
  那是把「一个可运行的脚本」换成「一堆互相关联的假设」。**阶段 3 出口必须先交付一次**
  （verify 跑通 + baseline 落盘就是第一个可判分点），4–5 是增量，不是下一个关卡。
- **停止条件**：门禁绿 + 验收清单逐项过 = 交付，到此为止，禁止自选加戏（再补断言、再重构、
  再压行数）。「还能更好」不是继续做的理由：调用方等的是能判分的产出。
- **改自己刚写的文件就改正文**：不要用 `scratch_patch.py` / `.fixN.py` 去打补丁——那是把改文件
  换成写解释器。**出现第二个一次性补丁脚本就是信号：该重写那个文件**。
- **预算先留收尾**：把最后一轮全量回归与写总结预留出来；预算将尽时停在能交付的最小完整状态、
  报告未完成项。超时的产出等于零。

## verify 脚本规范

- 独立可跑（`verify.py [--scope X] [--fix|--json]`），同时注册进工程统一命令入口。
- **`--fix` 只修派生数据**：重新生成一遍就能复原的东西（索引、生成物）。写证据、选版本、补理由一律不修——脚本代劳等于伪造。前置条件是 git 工作区**除目标文件外**干净：目标文件要排除，否则「提交被拦 → 修 → 再提交」这条最自然的恢复路径会被自己卡死；没有回滚点就改文件，比不改更坏。修完必须重跑，退出码只认重跑结果。可修清单跟断言住同一个文件（`FIXERS = {code: (修复函数, 会被重写的路径)}`），否则 code 就有两处定义。
- **一个 scope 一个文件**：`verify.py` 只做调度（读文件 + 注册表 + 排序输出），scope 实现放
  `scopes/<name>.py`，共用解析工具放 `scopes/common.py`。单文件长到改不动时，下一步就是写
  一次性补丁脚本打自己——实测十几次 `.fixN.py` 的轨迹，全部起于一个只会变大的单文件。
  本 skill 已照此拆过一遍：判据是**拆分前后 `--json` 输出字节等同**，不是「看起来更整齐」。
  机器判不了「这个文件算不算调度器」（语义），但判得了它退化成实现的体征：调度器里出现
  scope 专属正则常量、出现检查逻辑本体、或长到调度器不该有的体量——那是 `LAYOUT001`
  （正对照 `fixtures/ok-minimal` + 反向 `bad-inline-scope`）。适用面要说清：只在
  `<skill_dir>/scripts/audit.py` 存在时检查，不存在记 not_applicable，**不冒充通过**。
- **首版只上能守住的 scope**：新仓库 bootstrap 的上线 scope 数守住个位数以下（目录覆盖 + 链接/锚点这类能机器硬断言的），其余写进断言表标 TODO。没上线的 scope 不许在 `verify` 里声明——声明即承诺（见下）。
- 退出码契约：0 = 通过（可含 WARN），非 0 = 有 ERROR。
- scope 分域可单查，每个 scope 是独立函数，**每个新 scope 必须做反向测试**（造违规样本确认真的报 ERROR）——否则整个 scope 可能上线起就没执行过，跑一百次都「通过」。
- scope 分域就是独立的 conformance 单元：**声明即承诺**。UHP 里服务器不能广播自己没实现的能力，客户端信任它却收到 `404`，是无法恢复的欺骗。同一条规矩换个主语：入口给一条规则标了 scope，就等于承诺这个 scope 真的会拦；从上线起就没执行过的 scope，比不标更坏——它给了一个绿灯。所以每个 scope 上线前跑一次反向测试，按 scope 分开测、分开报，不拿总体「通过」掩盖某一域没测。
- **阶段不写死在脚本里**：阶段、顺序、门记录文件名、每阶段交付物只写在 `workflow/flow.json`；`gates` scope 读它，不维护第二份常量表。散文正文（`workflow/README.md`）只写「为什么、怎么做」，不重复列阶段。
