# 业务流程：Go 后端需求的 6 个阶段

一个需求从「接口定清楚」走到「灰度观察结束」，每阶段一个门记录。门记录是事实，不是仪式：
没有证据的 `pass` 由 `gates` scope 判 ERROR。

## 1 需求与接口契约（contract）

- **目的**：把「做什么」定到可测、可对接。
- **输入**：需求单、上下游调用方、现网指标。
- **执行**：写验收标准（每条 given_when_then 或 measure）；逐个接口写方法/路径/请求/响应/错误码/幂等性；
  写 NFR（性能、可观测、兼容性）各自的指标与验证方法。
- **产物**：`artifacts/contract.json`。
- **检查**：机器判 `contract`（CTR001–004）；人判需求价值与优先级。

## 2 方案设计（design）

- **目的**：把接口落到包边界上，并先想清楚会怎么坏。
- **输入**：契约、现有模块结构、依赖选型约束。
- **执行**：列包与职责、包依赖（必须无环、不得引用未声明的包）；每个关键决策记录**被否方案**；
  列失败模式（怎么发现、怎么缓解）。
- **产物**：`artifacts/design.json`。
- **检查**：机器判 `design`（DES001–004）；人判取舍理由是否成立。

## 3 编码实现（impl）

- **目的**：让代码形状和错误/并发纪律在评审前就成立。
- **输入**：方案、契约。
- **执行**：入口放 `cmd/<服务>/main.go` 且只做装配；业务放 `internal/`；导出符号写 doc 注释；
  错误用 `%w` 包装；库代码不自造 context、不 panic、不 `os.Exit`；跑 build/vet/lint。
- **产物**：`artifacts/impl.json` + 代码。
- **检查**：机器判 `layout`（LAY001–007）、`runtime`（RUNT001–007）、`impl`（IMP001–004）。

## 4 测试与自测（test）

- **目的**：证明行为符合契约，且并发安全、性能没退化。
- **输入**：契约、代码。
- **执行**：每个非 main 包写表驱动测试；跑 `go test -race ./...`；记录覆盖率（总/核心）；
  对热点路径跑 benchmark 并与基线比。
- **产物**：`artifacts/test.json`。
- **检查**：机器判 `test`（TST001–006）；人判测试是否覆盖了契约里的错误分支。

## 5 代码评审（review）

- **目的**：用第二双眼睛挡住「能跑但会烂」的改动。
- **输入**：MR、契约、方案。
- **执行**：控制 MR 体量；指定至少 2 名评审人并签字；作者不自批；每条意见闭环（`closed`）。
- **产物**：`artifacts/review.json`。
- **检查**：机器判 `review`（REV001–004）；人判可读性与设计质量。

## 6 发布与观察（release）

- **目的**：把「上线」变成有边界、可回退的动作。
- **输入**：已评审的 MR、冒烟用例、监控面板。
- **执行**：打 tag（`v<version>`）；定灰度比例与持续时间；写回滚触发条件、命令、责任人；
  跑冒烟（必须全绿）；按观察窗看错误率与 p99。
- **产物**：`artifacts/release.json`。
- **检查**：机器判 `release`（REL001–005）；人判灰度与观察窗是否匹配风险。

## 跨阶段：变更与例外

- 变更（`changes.json`）：类型、影响、审批人、通知对象、是否重新基线、回滚方式。
  契约变更必须通知上下游两方以上。
- 例外（`exceptions.json`）：责任人、理由、批准人、到期日。**到期未续期即 ERROR**——
  例外是限时通行证，不是永久豁免。

## 门记录怎么填

模板见 `.harness/stack-templates/gate-record.json`。`result` 只有三个值：

| 值 | 含义 | 额外要求 |
| --- | --- | --- |
| `pass` | 本阶段检查全过 | 必须有 `evidence` |
| `conditional` | 带例外通过 | 必须有未过期 `exceptions` |
| `reject` | 打回 | 必须有 `rework`，且后序阶段不得 `pass` |
