# 踩坑记忆

一条一个坑，三段缺一不可：现象 / 根因 / 落成的断言。**没有第三条的条目不算记忆**——
那只是抱怨。落成的断言要么指向 `scripts/scopes/` 里的一个 code，要么在 `AGENTS.md`
的「人判项」里写明强度来源。

## L-1 错误链在中间层断掉

- 现象：HTTP 层拿不到 `order.ErrNotFound`，只能靠字符串匹配，改文案就崩。
- 根因：中间层 `fmt.Errorf("get order %q: %v", id, err)` 用了 `%v`，错误链断了。
- 断言：`RUNT003`——`fmt.Errorf` 带 err 却没 `%w` 判 ERROR。

## L-2 入口膨胀成第二个业务层

- 现象：`cmd/ordersvc/main.go` 长到 300 行，里面写了下单校验和重试。
- 根因：装配与业务混在一起，main 没有行数约束。
- 断言：`LAY004`——`main.go` 超过 `main_max_lines` 判 ERROR，业务必须下沉到 `internal/`。

## L-2 断言存在，不等于断言覆盖到

- 现象：给 `links` 加上锚点校验后门禁全绿，而 32 处 references 锚点**一条都没被查**——
  因为 `check_relative_links` 拿的是 `ctx["text"]`，里面只有主文档一个文件。
- 根因：写断言时只想了「判什么」，没想「读哪些文件」。第二个消费方（references）加进来时，
  读取面没跟着扩，断言就成了只覆盖一半的假绿灯。
- 断言：`GATE007` 只判本文件三段式；本条属于「断言自身的覆盖边界」，**无断言、人判**——
  每次新增一个消费方时，回头确认 `verify` 的读取面是否跟着扩。

## L-3 新交付物第一次出现，必然没人点名

- 现象：连续三个新文件（`hooks.py`、`round.py`、`retro.py`）第一次提交都被同一条断言打回：
  文件在、有用、但文档一次都没提它。
- 根因：写机制的人注意力全在机制本身，而「谁点名它」是另一件事。「有了却没人说」与
  「说了却没有」是同一处脱钩的两面。
- 断言：`GATE007` 管 lessons 形状；「新文件必须进目录地图」在本模板由 `AGENTS.md` 的
  目录地图人判——模板里的机检项是 `STRUCT001`（根下条目要么在标准四件里，要么带理由声明）。
